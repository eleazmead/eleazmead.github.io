## Architecture

This is an **Angular 22** single-page application (SPA) bootstrapped with standalone components - no `NgModule`. The entry point is `src/main.ts`, which bootstraps `AppComponent` via `src/app/app.config.ts`.

### Key architectural decisions

- **Standalone components throughout.** Every component uses `imports: [...]` directly; there is no shared module.
- **Test runner is Vitest**, not Karma/Jasmine. Test types come from `vitest/globals` (see `tsconfig.spec.json`). The Angular CLI delegates to Vitest via `@angular/build:unit-test`.
- **SCSS, not CSS.** Despite the project being scaffolded with CSS intent, `angular.json` configures `inlineStyleLanguage: scss` and all component style files use `.scss`.
- **Multi-environment config.** Three environment files under `src/environments/` (`development`, `staging`, `production`). The production build sets `baseHref: /eleazmead/` for GitHub Pages hosting.
- **Path-based routing** with a `404.html` workaround for GitHub Pages. `postbuild` copies `index.html` → `404.html` so direct navigation to `/admin` works. No hash prefix.
- **`<main>` (`src/styles.scss`) has `position: relative; z-index: 1`**, needed to layer its own decorative `::before`/`::after` pseudo-elements. This means it establishes its own stacking context - any `position: fixed` full-screen overlay left INSIDE `<main>` gets its z-index compared only within that local context (capped at 1), no matter how high a value is set on the overlay itself, so a sibling of `<main>` like the fixed language toggle (`z-index: 1000`, rendered before `<main>` in `home.component.html`) can end up rendering on top of it even with `z-index: 1100` on the overlay. Any component that opens a full-screen `position: fixed` lightbox/overlay must reparent that overlay to `document.body` via `Renderer2.appendChild` (see `PolaroidPhotoComponent.moveOverlayToBody()` and `WhatToWearComponent.moveOverlayToBody()`) - a z-index bump alone does not fix this, since the overlay never actually escapes `<main>`'s stacking context without being moved in the DOM. This bit the What to Wear attire-guide lightbox's close button, which the language toggle was rendering on top of, until it was given the same body-reparenting treatment as the polaroid focus overlay.

### CI/CD

GitHub Actions (`.github/workflows/deploy.yml`) runs on every push/PR to `main`:

- PRs: builds with `--configuration development` (no deploy)
- Merges to `main`: computes build number → injects secrets → production build → deploys to GitHub Pages at `dist/eleazmead/browser`

**Build number** - `environment.production.ts`'s `buildNumber` field (rendered in the footer as `Build: <value>`, only for locales/environments where it's non-empty) is injected the same way as the secrets below: the workflow's "Compute build number" step formats the actual build time as `YYYY.DD.MM-<run number>` (UTC, via `date -u`) and passes it through as `REPLACE_BUILD_NUMBER`. The run number is GitHub Actions' own auto-incrementing counter for the workflow, used as the "iteration" suffix so same-day rebuilds are distinguishable without querying past runs. Local dev and staging (`environment.ts`/`environment.staging.ts` and their `.example` templates) hardcode `buildNumber: 'local'` instead, since there is no CI build to derive one from.

### App structure

`AppComponent` is a thin router shell (`<router-outlet />`). Routes:

- `/` → `HomeComponent` (`src/app/components/home/`) - the public wedding website
- `/:rsvpHash` → `HomeComponent` (`src/app/components/home/`) - public wedding website with an RSVP invitation hash from the URL path
- `/admin` → `AdminComponent` (`src/app/components/admin/`) - password-protected RSVP dashboard

The public site renders eleven standard sections in order: Hero → Our Story → Venues → RSVP → Wedding Timeline → What to Wear → Where To Stay → Gift Registry → Questions & Answers → Made With Love → Footer, all inside `HomeComponent`. A conditional Guest Letter section appears after Hero when the matched RSVP sheet row has both `LetterAddress` and `LetterMessage` and the URL RSVP hash either matches `FullNameHash_MD5` or matches a related guest hash with `LetterShowForAll` set to `1`.

**Config layer** - `src/app/config/app.config.ts` exports `APP_CONFIG` (`as const`), a typed constant holding non-copy configuration such as theme tokens, asset paths, stable option IDs, locale settings, and contact URLs. Do not put display text in `APP_CONFIG`; all user-facing text belongs in i18n JSON.

Notable `APP_CONFIG` fields:

- `assets.heroBackdropWebm` / `assets.heroBackdropMp4` — hero section background video, WebM primary with an MP4 fallback for browsers that can't play WebM (`HeroComponent`'s `<video>` binds both `<source>` tags to these rather than hardcoding paths). Regenerate the MP4 from the WebM via `ffmpeg` if the backdrop ever changes - see `public/hero/README.md` for the exact command. The video is paused via `IntersectionObserver` while the hero section is scrolled out of view and resumed on return, since browsers don't auto-pause off-screen `<video>` in a normal scrolling page and it would otherwise keep decoding frames for zero visual benefit, competing with everything else on the page (notably the Our Story polaroid scroll physics) for the same mobile CPU/GPU budget.
- `assets.attireGuideImage` — wedding attire guide image path under `public/`; blank or failed paths render a visible placeholder. The attire guide title lives in `whatToWear.imageTitle`; the image is centered at 70% width with a white border on stacked layouts, sits in a second desktop column beside the attire copy, and opens an enlarged lightbox view when clicked. The lightbox uses the same FLIP (First-Last-Invert-Play) grow/shrink transition and body-reparenting as the Our Story polaroid focus mode (`WhatToWearComponent.playOpenFlip`/`playCloseFlip`, mirroring `PolaroidPhotoComponent`) - the inline board image is concealed (`.what-to-wear__image-button--concealed`, `opacity: 0`) the instant focus mode opens, so it visibly grows from its exact on-page position into the centered overlay rather than a separate copy popping in on top of it, and reverses symmetrically on close.
- `assets.venuePhotos` — ceremony/reception venue photo paths under `public/`; blank or failed paths render visible placeholders. Real venue photos preserve their natural aspect ratio, are centered at 70% width within each venue item, have a white border, and must not be cropped. Venue items render in two columns on desktop.
- `mealChoices.options` — stable meal choice IDs (`beef` / `fish`); labels and descriptions live in i18n JSON
- `whatToWear.colorGuide` — configurable attire color swatches for ladies and gentlemen. The visible "Color guide" label lives in i18n JSON.
- `whereToStay.hotelGroups` — ordered stable hotel group and hotel IDs for the Where To Stay section; headings, hotel names, and descriptions live in i18n JSON
- `rsvp.deadlineDate` — machine-readable RSVP cutoff date in `YYYY-MM-DD` format. The displayed deadline copy still lives in i18n JSON.
- `questionsAndAnswers.items` — ordered stable Q&A IDs; matching `questionsAndAnswers.items.<id>.question` and `.answer` text must exist in i18n JSON
- `contacts.whatsappUrl` — WhatsApp CTA link used in the RSVP not-found state
- `i18n.defaultLocale` / `i18n.supportedLocales` — locale configuration for the language toggle and translation service

**Visual direction** - The site follows a wedding mood board of light brown and black with white space, blush pink floral accents, and taupe neutrals. Global styling uses a subtle wedding-stationery background with vellum warmth, lace-like linework, and soft blush/taupe washes. Keep the look refined, romantic, candlelit, and editorial rather than bright, playful, or highly saturated.

**Responsive spacing** — Public content sections use tighter mobile-first vertical padding, then expand at desktop breakpoints. Preserve the compact mobile rhythm when adding sections so the page does not feel overly spaced on phones.

**i18n** — All display text lives in `public/i18n/en.json`, `public/i18n/fil.json`, and `public/i18n/zh.json` (Mandarin Chinese as used in Singapore - Simplified characters, `hreflang`/`og:locale` tagged `zh-Hans-SG`/`zh_SG` rather than bare `zh`). Keep all three files structurally complete (identical key paths) whenever adding or changing copy - a mismatch silently falls back to English per-key rather than erroring. `TranslationService` (`src/app/shared/translation.service.ts`) fetches `public/i18n/{locale}.json` at runtime via `HttpClient`. `APP_CONFIG.i18n.supportedLocales` is the single source of truth for which locales exist - `LanguageToggleComponent`'s dropdown and `SeoService`'s hreflang/og:locale:alternate tags both iterate it rather than hardcoding locale lists, so adding a fourth locale only requires a new `public/i18n/<code>.json`, a `supportedLocales` entry, an `ogLocaleMap` entry, and (if its hreflang/OG code differs from the internal short code, as `zh` does) a case in `SeoService.hreflangFor()`. A `pure: false` `TranslatePipe` exposes `'key.path' | translate` to templates. When a non-English locale's value is empty, the service falls back to the `en.json` value automatically. `provideHttpClient()` must be present in `src/app/app.config.ts` (Angular's ApplicationConfig) for this to work.

- **Language toggle is a dropdown, not a binary switch** (`src/app/shared/language-toggle/`) - a fixed top-right trigger button shows the current locale's short label (`EN`/`FIL`/`中文`) beside a chevron that rotates 180° when open, and clicking it opens a small menu listing every locale in `APP_CONFIG.i18n.supportedLocales` (via `languageToggle.labels.<code>`, present in every locale file so the labels remain readable regardless of which locale is currently active). Closes on outside click (`HostListener('document:click')` checking `!elementRef.nativeElement.contains(event.target)`) and on Escape.

- `hero.headline` in `public/i18n/en.json` includes a `{0}` placeholder. `HeroComponent` replaces it with the first word of the matched guest name from `FullName`, `Guest1Name`, or `Guest2Name` after resolving the URL RSVP hash. When the Guest Letter section is shown, the placeholder uses `LetterAddress` instead. When no RSVP hash is present, the placeholder uses `hero.noInputGreeting`.
- While the matched guest name is loading, the hero renders `Hi there,` at the start of the headline rather than showing fallback guest text.
- The hero places the wedding date above the couple names, and the ceremony/reception details render as two glow-backed text columns on desktop, collapsing to one column with extra spacing on mobile. Avoid box-like containers for these date and venue details. Ceremony/reception times live in `hero.ceremonyTime` and `hero.receptionTime` in i18n JSON.
- Section headings use plain display text without decorative `::after` underline elements.
- The hero RSVP CTA keeps `href="#rsvp"` for semantics but also calls `HeroComponent.scrollToRsvp()` so scrolling targets `.rsvp__container` reliably on path-param invitation URLs. It performs a short follow-up alignment to absorb layout shifts from media above RSVP. When the Guest Letter section is shown, the CTA is hidden in Hero and rendered centered at the bottom of the letter instead.
- The scroll-down chevron calls `scrollDown($event)` which always calls `event.preventDefault()` - without this, Angular's router intercepts the hash anchor on `/:rsvpHash` routes and navigates to root `/`, stripping the hash from the URL and losing the guest letter. It then manually calls `scrollIntoView()` targeting `#guest-letter` when `shouldMoveRsvpCta()` is true (Guest Letter section is shown for this invitation), otherwise `#our-story`.
- **The Google Fonts `<link>` in `src/index.html` deliberately keeps `display=swap`, not `display=optional`** - `.hero__content` (the large Cormorant Garamond couple names/headline) was Lighthouse's single largest layout-shift culprit (CLS 0.169) purely from the web-font swap, and `display=optional` (falls back to the system font for that page load's entire lifetime if the custom font doesn't load within a short block window, avoiding the reflow) was tried as a fix - but it visibly broke the brand's serif display font on real loads far more often than expected, which matters far more here than the CLS score. Don't reintroduce `display=optional` for this reason. A proper fix (self-hosting the fonts with `size-adjust`/`ascent-override`/`descent-override` metric overrides so a `swap` reflow becomes near-invisible even when it happens) is a viable follow-up but hasn't been attempted.
- The conditional Guest Letter section uses the matched `/:rsvpHash` row. It renders only when both `letterAddress` and `letterMessage` are non-empty and the hash source is either `FullNameHash_MD5` or a related guest hash (`Guest1FullName_MD5` / `Guest2FullName_MD5`) with `letterShowForAll` set to `1`. It formats the message like a handwritten white letter with subtle burnt edges and uses `guestLetter.signatureLine` for the closing. The signature name uses `LetterSignedBy` from the sheet when present, otherwise falls back to `guestLetter.coupleName` from i18n.
- Couple names, event date, venue names/descriptions/addresses, Our Story timeline dates/titles/body copy, RSVP copy, meal labels/descriptions, Wedding Timeline event times/titles/descriptions, What to Wear copy and color-guide label, Where To Stay copy and hotel labels, Gift Registry copy, Questions & Answers copy, footer copy, language toggle labels, and admin/export labels all live in i18n JSON.

**Animations** - Hero uses CSS `@keyframes` fade-in with staggered delays. Section headings use `FadeUpDirective` (`src/app/shared/fade-up.directive.ts`) which attaches an `IntersectionObserver` and adds `.fade-up--visible` when the element enters the viewport. The `.fade-up` / `.fade-up--visible` classes are defined globally in `src/styles.scss` (they can't be scoped because they're applied programmatically). The observer uses `rootMargin: '0px 0px 120px 0px'` (120px lookahead below the viewport) so elements already near the viewport on page load - such as Our Story or the Guest Letter section on short mobile viewports - animate in immediately without requiring a scroll gesture.

**Our Story photos** - Timeline images are convention-based and do not live in `APP_CONFIG`. Put files in `public/our-story/` using `Mmm_YYYY_1` for the required first image and `Mmm_YYYY_2` for the optional second image, for example `Sep_2016_1.png` and `Sep_2016_2.jpg`. The month must be the 3-letter abbreviation (`Apr`, not `April`) and the `_1`/`_2` slot number is required even for a single photo. Supported extensions are `.jpg`, `.jpeg`, `.png`, and `.webp`; filename matching is case-insensitive. This same extension list is enforced in TWO places that must stay in sync: `STORY_IMAGE_EXTS` in `scripts/generate-gallery-manifest.mjs` (filters which files even make it into the manifest) and the filename-parsing regex in `OurStoryComponent.photosByPrefix()` (parses `Mmm_YYYY_N.ext` back out of the manifest) - adding a new extension to only one of the two silently drops matching photos. The manifest generator writes `public/our-story/manifest.json`, and `OurStoryComponent` maps actual filenames from that manifest. The site renders up to two images side by side per timeline item and ignores higher image numbers. Missing images fall back to a visible placeholder. **After adding new photos, the manifest must be regenerated** - restart `npm start`/`npm run build` (their `prestart`/`prebuild` hooks run the generator automatically), or run `npm run generate-gallery` manually. Running `ng serve`/`ng build` directly skips these hooks and will not pick up new files.

- **The manifest carries each photo's actual intrinsic pixel dimensions, not just its filename** - `scripts/generate-gallery-manifest.mjs` reads them at generation time via the `image-size` package (a devDependency), writing `public/our-story/manifest.json` as `{ file, width, height }[]` rather than a plain filename array. `OurStoryComponent.photoWidth()`/`photoHeight()` look these up per photo URL and pass them to `PolaroidPhotoComponent`'s `imageWidth`/`imageHeight` inputs, which render as native `width`/`height` attributes on the `<img>` (`PolaroidPhotoComponent` never crops/forces an aspect ratio from them - `.polaroid__photo` still uses `width: 100%; height: auto` for its actual rendered size; the attributes only give the browser the correct aspect ratio to reserve space with before the image loads). This directly addresses Lighthouse's "unsized images" audit and a meaningful chunk of cumulative layout shift on a page with a dozen-plus photos - an image with no size hint collapses to 0 height until it loads, then the whole page jumps. This is fully automatic: adding a new photo and rebuilding (or restarting the dev server) is still the entire workflow: no manual dimension entry anywhere.

- Photo captions: `ourStory.timeline.<id>.photoCaption1` / `photoCaption2` in i18n JSON. `.polaroid__caption` wraps onto up to 2 lines (`-webkit-line-clamp: 2`) before clamping with an ellipsis, rather than truncating to a single line - most captions fit comfortably in two short lines. `MAX_CAPTION_LENGTH` in `PolaroidPhotoComponent` (110 chars) is just a generous safety net against a genuinely runaway-long string, not the primary truncation mechanism. One caption per photo slot, following the same `Mmm_YYYY_1`/`_2` ordering as the filenames.

**Polaroid photo component** (`src/app/shared/polaroid-photo/`) - Renders each Our Story photo as a pinned, physically-animated polaroid card. Used only by `OurStoryComponent`; inputs are `imageUrl`, `alt`, `caption` (no `seed` input - removed in favor of hash-derived physics, see below).

- **Frame sizing**: no fixed aspect-ratio. `.polaroid__frame`/`.polaroid__photo` use `width: 100%; height: auto`, so the card's height follows each photo's own natural aspect ratio (portrait, landscape, or square) rather than cropping everything to a square, like real varying-format instant-film prints.
- **Deterministic per-photo physics, not random-per-load**: `rotationDeg`, `staticOffsetPx`, `sensitivityMultiplier`, `settleDelayExtraMs`, and `springDurationS` are all derived from a FNV-1a hash (`hash01()`) of the photo's own `imageUrl`, each with a distinct salt string. Same photo always produces the same tilt/physics on every load (stable, not flickering) - adding a new photo automatically gets its own well-distributed values with zero configuration. Do not reintroduce a small index/array-based "seed" system; a short lookup table indexed by a low integer clusters similar values on nearby indices (this was tried and reverted).
- **Gravity-correct pin position**: a card pinned exactly above its own center of mass hangs straight; any resting tilt must come from the pin being offset from center (equilibrium: the pin-to-centroid line must hang vertical). `applyPinShift()` in `PolaroidPhotoComponent` measures the ACTUAL rendered card width/height (via `offsetWidth`/`offsetHeight`, after image load and on `ResizeObserver` changes) to compute this, rather than assuming fixed proportions - the card's height now varies per photo (see frame sizing above), so a hardcoded formula would be wrong. `--polaroid-pin-shift` (a CSS custom property) drives both the pin's horizontal position and the focused figure's `transform-origin: 50% 50%` override; the two must always match or the pivot point drifts from the pin's visual needle-tip position (`PIN_ANCHOR_PX` constant).
- **CSS custom properties set via `Renderer2.setStyle` must pass `RendererStyleFlags2.DashCase`** as the 4th argument, or Angular silently no-ops the write (falls back to `el.style[name] = value`, which does not work for `--`-prefixed custom properties). This bit us for `--polaroid-parallax`, `--polaroid-inertia-tilt`, and `--polaroid-pin-shift`. This gotcha only applies to `Renderer2.setStyle` - `PolaroidScrollPhysicsService` (below) uses plain `element.style.setProperty()` directly, which does not need the flag.
- **Parallax lives on `:host`, not on the card** - `--polaroid-parallax` is applied as `transform: translateY(...)` on the `:host` element so the pin SVG and the card translate as one rigid assembly. If parallax were on `.polaroid` only, the pin (absolutely positioned inside `.polaroid-mount`) would stay put while the card shifted, creating a visible gap between needle and card surface during scrolling. The overlay is reparented to `<body>` on open so it is never a descendant of `:host`; `--polaroid-parallax` does not inherit there and defaults to 0.
- **Resting tilt capped at `MAX_REST_TILT_DEG = 5`** - reduced from 7 to prevent cards overflowing narrow mobile column widths while preserving the physical corkboard look.
- **Scroll physics runs through a single shared service, not per-instance**: `PolaroidScrollPhysicsService` (`polaroid-scroll-physics.service.ts`) drives parallax and scroll-inertia tilt for every polaroid on the page from ONE `window` scroll listener and ONE `requestAnimationFrame` loop, instead of each `PolaroidPhotoComponent` running its own. Each frame it does a strict batched read-phase (every `getBoundingClientRect()` across all registered photos) then write-phase (every style/class mutation) - this was a deliberate fix for iOS Safari scroll jank, since N independent per-instance loops interleaving their own reads and writes causes layout thrashing (every write invalidates layout, forcing the next instance's read to force a synchronous recalculation). Components `register()`/`unregister()` a lightweight handle in `ngAfterViewInit`/`ngOnDestroy`. Velocity is smoothed over a rolling 300ms window of scroll samples (computed once here, shared by all photos) rather than a single animation-frame delta, which is too noisy from real trackpad/wheel input. The window is 300ms (not shorter) because Windows mouse wheel fires events ~150-250ms apart; a shorter window would let the previous sample age out before the next event, making every velocity read 0 and suppressing tilt entirely.
- **Inertia tilt magnitude is a continuous function of scroll speed, with no minimum-speed cutoff** - `inertiaTilt = sign * MAX_INERTIA_TILT_DEG * (1 - e^(-TILT_RESPONSE_K · speed))`, computed for every scroll tick regardless of how slow it is. An earlier version gated the whole tilt calculation behind `FLICK_VELOCITY_THRESHOLD` (0 below it, curve above it) with a steep `K` - since real scroll gestures cross a low threshold almost immediately, that made the swing jump straight to a large, near-constant value the instant ANY scrolling started, which read as "the same swing regardless of how fast or slow I scroll" (reported directly). `K` is now low enough that a slow, deliberate scroll produces a barely-there sway while a fast flick ramps up smoothly toward `MAX_INERTIA_TILT_DEG`, with no discontinuity in between - see the constants' doc comments in `polaroid-scroll-physics.service.ts` for the reasoning and example values at different speeds.
- **`FLICK_VELOCITY_THRESHOLD` (1.5 px/ms) only chooses the transition _style_, not whether tilt applies at all** - at/above it, `.polaroid--scrolling` (a near-instant 0.06s-linear transition) swaps in so fast flicks visibly snap-track; below it, the same continuously-computed tilt still applies but eases via the slower, smoother spring transition instead of snapping. Set at 1.5 so typical Windows mouse wheel (~0.5 px/ms) always stays below it and uses the smooth spring; Mac/iOS trackpad fast flicks exceed it. `INERTIA_SETTLE_MS` is 250ms (not 120ms) so the settle timer never fires between consecutive Windows wheel events (~200ms gap) and cause a mid-scroll spring-back oscillation.
- **Notched wheel detection suppresses inertia tilt** - a passive `wheel` listener checks `WheelEvent.deltaMode > 0` (DOM_DELTA_LINE, always a notched wheel) or `|deltaY| >= 100` (notched wheel normalised to pixels by Windows/Chrome; Mac trackpad is always < 10px per event). When active, tilt is suppressed entirely - discrete notch steps have no smooth physical equivalent and any swing looks like jitter. The flag clears 500ms after the last notched event so switching to a trackpad re-enables animation immediately. This listener does zero DOM work per event (two comparisons + flag + setTimeout); the `continue` path in the write loop also saves the per-card `exp()` and two `setProperty` calls.
- **`.polaroid`'s scroll-driven tilt is a single combined `transform` (translate3d + rotate + scale), not the individual `rotate`/`translate`/`scale` CSS properties it used to use** - those individual properties (CSS Transforms Level 2) don't have as mature/consistent GPU-compositing support across browsers, notably Safari/WebKit, as the long-standing `transform` shorthand does. This is the exact same class of bug already fixed for the FLIP focus-mode transition (see `flipTransform()` below) - the difference is this scroll-driven animation runs on every scroll frame, far more often than FLIP (which only runs once per open/close), so it was actually the more performance-critical path and was reported as laggy specifically on iOS Safari while smooth on desktop, matching this bug's known browser-specific signature. Because `rotate`/`translate`/`scale` used to transition independently (rotate on a springy duration, scale on a quick `0.3s ease` for hover), merging them into one `transform` means they now necessarily share a single transition timing - hover's zoom trades its previous snappier `0.3s` for the spring duration, a small deliberate cosmetic compromise for the much bigger compositing win during scroll.
- **The pin uses a single `transform` shorthand** (not individual `translate`/`rotate`/`scale` CSS Level 2 properties) for the same GPU-compositing reason as the card. The pin lift/settle animation was invisible on Windows Chrome with individual properties.
- **Viewport-proximity culling**: `PolaroidScrollPhysicsService` only reads/writes photos currently within one of two always-running `IntersectionObserver` bands around the viewport (`NEAR_ROOT_MARGIN` for idle/slow scrolling, wider `FAR_ROOT_MARGIN` once scroll speed crosses `FAR_TIER_SPEED_THRESHOLD`) - far off-screen photos (Our Story can have well over a dozen) are skipped entirely each frame, not just avoiding thrashing but avoiding the read+write work itself, since their computed values are invisible anyway. Both bands run continuously in the background at effectively zero cost; "switching" bands based on scroll speed each frame is just choosing which precomputed active `Set` to consult, never recreating an observer (recreating one on every velocity change would itself be expensive/thrashy). `rootMargin` percentages resolve against the viewport (`root: null`), so both bands scale automatically with viewport height - no separate mobile/desktop tuning needed.
- **`will-change` is scoped to only actively-animating states**, never applied permanently to the base `.polaroid` rule - with a dozen-plus photos on Our Story, permanently promoting every card to its own compositor layer wastes GPU memory even for off-screen ones. It's applied to `.polaroid--scrolling`/hover for the scroll physics, and imperatively via JS for the duration of the focus-mode FLIP transition only (see below).
- **Focus/lightbox mode is a FLIP transition (First-Last-Invert-Play), not a simple pop-in/fade**: clicking a photo doesn't just show a centered overlay - the overlay card visibly grows FROM the inline photo's exact on-page position/size/rotation into the centered focused view, and reverses symmetrically on close (shrinks back down and lands exactly where the pin re-pins it). Two signals: `focused` (drives the pin lift/reveal and inline-card concealment, flips immediately on open/close) and `overlayVisible` (controls the overlay's DOM presence, kept separate so the overlay can stay mounted for the full duration of the closing shrink animation instead of vanishing the instant close is clicked).
  - `open()` captures the inline card's `getBoundingClientRect()` center position plus `rotationDeg()` and `offsetWidth`/`offsetHeight` BEFORE any state changes. `getComputedStyle(card).rotate` is NOT used - the card's rotation comes from the CSS `transform` shorthand (`var(--polaroid-rotate)`), not the individual `rotate` property, so `getComputedStyle().rotate` always returns `none`. `offsetWidth`/`offsetHeight` are stored separately from `getBoundingClientRect()` because a rotated element's bounding rect is the axis-aligned bbox (expanded by the tilt angle), which would inflate the FLIP scale factor. The overlay uses `offsetWidth`/`offsetHeight` for scale and `getBoundingClientRect` center for position. The overlay is rendered in the component's normal tree first, then reparented to `document.body` via `Renderer2.appendChild` (triggered with `afterNextRender`) - `FadeUpDirective`'s `transform` on an ancestor would otherwise become the containing block for the overlay's `position: fixed` and clip it to that ancestor's box instead of the viewport. `playOpenFlip()` then measures the overlay's natural centered rect, computes the delta, and animates from an inverted (looks-like-inline) starting transform to identity.
  - The overlay card always receives `--polaroid-rotate: 0deg` and `--polaroid-offset: 0px` via template context (the `polaroidVisual` ng-template takes `rotDeg` and `offsetPx` as context variables; the inline mount passes the real hash-derived values, the overlay always passes 0). This is the correct fix for the focus-mode tilt bug - a previous attempt to keep `transform` inline after the open animation was reverted since the root cause is the variable binding, not the cleanup.
  - `close()`/`playCloseFlip()` does the reverse: shrinks the overlay back to the inline card's position/size/tilt. `endRotate` is read from `rotationDeg()` directly (same reason as above - `getComputedStyle().rotate` returns `none`). Scale uses `card.offsetWidth / overlayCard.offsetWidth`. `box-shadow` is snapped instantly to the inline card's computed value at the start (not animated - it is not GPU-compositable and animating it would force a CPU repaint every frame). The backdrop dims out via `background-color` alpha on the overlay root, not `opacity` (opacity cascades to children via compositing). Close uses `FLIP_CLOSE_TRANSITION_MS = 580ms` and `FLIP_CLOSE_EASING = cubic-bezier(0.34, 1.2, 0.64, 1)` (softer spring than open) for a gentler landing. At completion, the overlay card fades out over 0.15s while the inline card simultaneously fades in via its `opacity 0.2s ease` CSS transition - this crossfade eliminates the swap flash that would otherwise occur when removing the overlay and revealing the inline card at the same instant.
  - Completion is driven by the real `transitionend` event (checked against `event.propertyName === 'transform'`), not a fixed `setTimeout` matching the expected duration - a timer isn't frame-accurate against the actual CSS transition, and firing even slightly early yanks the overlay out mid-motion (a visible pop/flash right at the end). A `setTimeout` slightly longer than the expected duration remains only as a safety net in case `transitionend` never fires.
  - The animation itself is driven by a single combined `transform: translate3d(x, y, 0) rotate(deg) scale(sx, sy)` (via `flipTransform()`), NOT the individual `rotate`/`translate`/`scale` CSS properties used elsewhere in this component for the resting swing/hover physics. The individual-properties API (CSS Transforms Level 2) does not have as mature/consistent GPU-compositing support across browsers - notably Safari/WebKit - as the long-standing `transform` shorthand; switching to `translate3d` (the classic cross-browser GPU-layer-promotion trick) is what actually resolved stutter that persisted even after adding `will-change` hints and dropping `box-shadow` from the animated properties. `box-shadow` is deliberately excluded from the FLIP transition entirely (it just snaps) since it is not GPU-compositable and forces a CPU repaint every frame if animated.
  - Opening and closing use different easing: `FLIP_OPEN_EASING` (`cubic-bezier(0.22, 1, 0.36, 1)`, fast-start/long-decelerate, good for "growing into view") vs `FLIP_CLOSE_EASING` (`cubic-bezier(0.34, 1.2, 0.64, 1)`, a softer spring that lands gently rather than bouncing) so landing reads as placing the photo carefully back rather than snapping it down.
  - Respects `prefers-reduced-motion: reduce` via an explicit `window.matchMedia` check in JS (inline styles would otherwise override the stylesheet's own reduced-motion rules).
- **Pin concealment is scoped to `.polaroid` only** - `.polaroid-mount--concealed` does NOT set `opacity: 0` on the mount itself; it only hides the `.polaroid` card element via a nested rule. The pin SVG is a sibling of `.polaroid` inside the mount and is therefore NOT hidden, so users see it visibly lift off the board as the photo enters focus mode. `opacity 0.2s ease` is included in `.polaroid`'s transition list for the same reason (must be on the card, not the mount).
- Photo depth: the print is rendered as a separate recessed layer from the white card, not fused - `.polaroid__frame` has a small padding gap (slightly darker than the card) around the photo, and `.polaroid__photo` carries inset (not outward) box-shadows so it reads as sunken beneath the card's surface.
- The card's white mat has a CSS-only paper-grain texture (inline SVG `feTurbulence` data URI on `.polaroid` background) - no image asset. `numOctaves` is kept low and `stitchTiles` is dropped to limit Safari/WebKit SVG-filter rasterization cost.

**Made With Love section** (`src/app/components/made-with-love/`) - Renders after Questions & Answers, before Footer. Reuses the existing `footer.message` i18n key ("Website Made with Love by the Groom and the Bride.") rather than duplicating the copy - `FooterComponent` no longer renders this text itself (its `.footer__message` paragraph and SCSS rule were removed) since it would otherwise be shown twice on the page.

- Six source images live in `public/made-with-love/` as WebP, not PNG: `eleaz1.webp`/`eleaz2.webp`/`eleaz3.webp` and `mead1.webp`/`mead2.webp`/`mead3.webp`, ~800x800px. The original PNG exports were 2380x2380px and 3-5MB each (~24MB total) - decoding six of those plus filter compositing on top caused real, reported page jank/hangs when the section scrolled into view. Any replacement images must stay web-optimized (roughly this resolution, comparable file size) - re-adding oversized source images will reintroduce the hang. Angular's built-in `NG0913` dev-console warning (oversized intrinsic image dimensions vs. rendered size) is a leading indicator if this regresses.
- The animation only starts once the section scrolls into view (`IntersectionObserver`, threshold `0.4`), not on page load - `ngAfterViewInit` observes the host element and triggers `startAnimation()` on first intersection.
- "GIF" playback is a plain `setInterval` cycling a `frameIndex` signal through 0/1/2, swapping each figure's `src` between its three frames every 550ms - no actual GIF/video asset. Both figures share the same `frameIndex`, so eleaz and mead animate in sync with the caption text centered between them.
- Plays through 6 full 3-frame loops (`LOOP_COUNT = 6`) at 400ms per frame (`FRAME_INTERVAL_MS = 400`), tracked by counting how many times `frameIndex` wraps back to 0, then transitions to a `frozen` phase.
- In the `frozen` phase playback simply stops with `frameIndex` back at 0 - both figures land on and stay on their first frame (`eleaz1.webp`/`mead1.webp`). The caption stays visible the whole time (never hidden) since this is meant to read as the section settling into its permanent resting state, not a transition into a different layout. An earlier version scattered all 6 static frames into a "fanned deck of cards" layout and hid the caption at this point; that was replaced with the simpler freeze-on-first-frame behavior; don't reintroduce the scattered-deck layout without a specific reason.
- This only plays once per page load: a `window scroll` listener resets `phase` back to `pending` (replaying the animation) only when the user scrolls back to the very top (`scrollY <= 4`) while already in the `frozen` phase - scrolling past the section again afterward does not replay it.
- Both figures are bottom-anchored (`align-items: flex-end`) with a breakpoint-scaled negative `margin-bottom` that pushes each image slightly past the section's own `overflow: hidden` bottom edge, cropping a small amount off the feet/hands so the images read as planted into the section rather than floating free. Keep this crop subtle (single-digit px) - an earlier, much larger crop amount cut the figures off at the shoulders and had to be walked back. `.made-with-love__text` sets `align-self: center` so the caption doesn't inherit the row's bottom alignment and sink down with the images.
- **Below the 640px breakpoint, the layout deliberately differs from desktop**: the two figures sit side by side (nearly touching, via `width: clamp(8rem, 46vw, 12rem)` and a small negative horizontal margin) with the caption on its own full-width line above them, rather than desktop's figure/caption/figure single row. This is done with `.made-with-love__stage { flex-wrap: wrap; }` plus `.made-with-love__text { order: -1; flex: 1 1 100%; }` - the 100%-basis caption forces itself onto its own line and the CSS `order` moves it before the (DOM-order-wise later) figures, so the two auto-basis figures wrap onto the next line together. Both the `order` and `flex-basis` reset back to inline-between-the-figures at 640px.
- Depth comes from a single soft-blurred `filter: drop-shadow(0 4px 6px …)` (30% opacity of `--color-secondary`), shared via the `--made-with-love-sticker-shadow` custom property, applied to both figures. `drop-shadow` (not `box-shadow`) is required here since these are transparent die-cut PNGs/WebPs - `box-shadow` is confined to the rectangular element box and would show a visible rectangle around the transparent padding, while `drop-shadow` follows the actual alpha silhouette. An earlier iteration tried building a hard sticker-style outline by stacking many crisp `drop-shadow()`s around a circle in a Sass `@for` loop; that was replaced because (a) the CSS `filter` property requires its filter functions **space-separated, not comma-separated** - joining the Sass list with `comma` silently produced an entirely invalid `filter` value that computed to `none` with no error, and (b) once fixed, a hard outline read as too heavy/thick at every thickness tried and did not match the desired soft-lift look. Don't reintroduce the multi-shadow outline approach without a specific reason; the single soft shadow is the settled direction.

**RSVP Google Sheets integration** - RSVP is backed by two Google services:

- **Reads** (guest list): Google Sheets REST API v4 GET via `SheetsService.fetchGuestList()`.
- **Writes** (submissions): Google Apps Script Web App POST via `SheetsService.submitRsvp()`. Uses `Content-Type: text/plain` to avoid CORS preflight.
- Config lives in `src/app/config/sheets.config.ts` (`SHEETS_CONFIG`), which reads `apiKey`, `spreadsheetId`, and `gasWebAppUrl` from the environment file. Fill these into `environment.ts` locally (see "Local setup after cloning"). The spreadsheet must be shared as "Anyone with the link can view".
- RSVP lookup is invitation-link based. The public route `/:rsvpHash` reads an MD5 hash from the URL path and `GuestSearchService` (`src/app/shared/guest-search.service.ts`) matches it against `FullNameHash_MD5`, `Guest1FullName_MD5`, or `Guest2FullName_MD5` after trimming whitespace and normalizing case. The bare `/` route shows an invite-only message instead of a search form.
- **RSVP state machine**: `idle → no_invitation_link / searching → found → confirming → submitting → success / not_found / error`. Once in `success`, there is no reset.
- **rsvpRaw structure**: always keyed by `row.fullName` (primary guest), with one flat `RsvpEntry[]` covering all group members. When a related guest responds separately, their entry is merged into the existing array (preserving others). Never use separate initiator keys.
- **Meal selection**: each attending guest must pick a main course (beef or fish). `MealChoice` is stored on `RsvpEntry`. `rsvpBeefCount` / `rsvpFishCount` are sent in the submission payload and written to sheet columns F / G.
- **Meal validation**: the main-course required error is cleared whenever a guest's attendance or inclusion state changes, so the error never remains visible after a guest declines or is excluded.
- **RSVP note**: when an invitation hash is present, the RSVP section renders a configurable note from i18n, with `rsvp.deadline.date` emphasized separately from the surrounding copy. The bare `/` invite-only state does not show this note.
- **RSVP deadline gate**: `APP_CONFIG.rsvp.deadlineDate` is compared against the current Singapore date. If the current date is later than or equal to the deadline date, new RSVP submissions and updates are blocked and the RSVP section shows `rsvp.deadline.closedMessage`.
- **RSVP review reminder**: the found-state form shows `rsvp.reviewReminder` immediately above the "Review your RSVP" button. Keep this venue reminder in i18n JSON.
- **RSVP review scroll**: after a successful "Review your RSVP" click, `RsvpComponent` realigns `.rsvp__container` after the confirming panel renders so the viewport does not drift into the Wedding Timeline section on mobile.
- **rsvpTotal** counts only `RSVP: true` entries across the merged array (not just the current submission). Computed from `mergedEntries.filter(e => e.RSVP).length` before submitting.
- **Related guests** default to `included: false` - users must explicitly include them.
- **Already-responded check** is per-guest (looks for the initiator's name in the entries array), not per-row. A related guest excluded by the initiator can still search and respond separately; they'll see other group members' responses as read-only.
- **RSVP updates**: a guest who has already RSVP-ed can use their invitation link before the deadline to update their own attendance and main course. Existing values are prefilled from `rsvpRaw`; submitting replaces that guest's entry while preserving other guests' entries.
- **Already-responded message** shows who submitted (`row.rsvpSubmittedBy`), falling back to the first key in `rsvpRaw` for older rows.
- All timestamps use SGT (UTC+8) via `nowSGT()` in `src/app/shared/utils/date.utils.ts`, producing ISO 8601 with `+08:00` offset.
- Data models: `GuestRow`, `RsvpEntry`, `MealChoice`, `RsvpRawPayload`, `RsvpSubmission` in `src/app/shared/models/guest.model.ts`; `LogRow` in `src/app/shared/models/log.model.ts`.
- Signal reactivity with Map: always create `new Map(this.selections())` when mutating - in-place Map mutations do not trigger Angular change detection.

**Admin page** (`/admin`) - Password-protected RSVP dashboard:

- Password verified server-side via GAS. The Angular bundle contains no password or hash. On login, the browser computes SHA-256 of the input via `crypto.subtle` and POSTs `{ action: 'verifyAdmin', passwordHash }` to the GAS endpoint. GAS compares the hash against `ADMIN_PASSWORD_HASH` stored in Script Properties and returns `{ authorized: boolean }`.
- **One-time owner setup:** open Extensions > Apps Script, select `setupAdminPasswordHash`, run it, and enter your password. It computes the SHA-256 hash via `Utilities.computeDigest` and stores it in Script Properties. The raw password is never stored anywhere.
- **Session persistence:** on successful login, `{ expiresAt: Date.now() + 8h }` is written to `sessionStorage` under key `eleazmead_admin`. On page load, `ngOnInit` reads this key; if the session is valid, the dashboard opens without a GAS round-trip. Session clears when the browser tab is closed or on explicit logout.
- **Logout button** in the header clears `sessionStorage`, resets all component signals to initial state, and returns to the login gate.
- Fetches guest list live from Sheets on login. Manual refresh button available.
- Table enumerates all individual guests (not grouped by row) with: Guest Name, Party Of, Meal Choice, RSVP badge, Date Submitted, Copy Invitation Link.
- The table includes a "Copy Invitation Link" button for each individual guest. It copies `window.location.origin + '/' + <guest-specific MD5 hash>` using `FullNameHash_MD5`, `Guest1FullName_MD5`, or `Guest2FullName_MD5` depending on the row.
- **Summary cards** show Total / Attending / Declined / Pending / Beef / Fish counts using elegant outline SVG icons (not emoji). Cards use CSS Grid: `repeat(3, 1fr)` on mobile, `repeat(6, 1fr)` on desktop - ensures all 6 cards always fit in two rows on mobile rather than the sixth wrapping alone. The beef icon is a rounded-rectangle steak slab with two diagonal marbling lines; the fish icon is a fish outline with a forked tail. Attending/declined cards have a green/red tinted background and their icon inherits a matching tint.
- **Header buttons** (Refresh, Export Excel) use inline outline SVGs instead of Unicode arrows.
- **Sticky first column** - the "Guest Name" `th` and `td` cells use `position: sticky; left: 0` so the guest name stays visible when the table scrolls horizontally. A `box-shadow: 1px 0 0 #2a2a2a` on the sticky cells creates a visual separator without disturbing table layout.
- **Multi-column sorting** - all five data columns (Guest Name, Party Of, Meal Choice, RSVP, Date Submitted) are sortable. Clicking a column header cycles: no sort → ascending → descending → no sort. Multiple columns can be sorted simultaneously; priority is the order they were clicked. The sort state is held in `sortColumns: Signal<SortEntry[]>` (`SortEntry = { key: SortKey; dir: 'asc' | 'desc' }`). `sortedRows` is a `computed()` that applies all active sorts in priority order to `adminRows()`. Sort indicators use a chevron SVG that dims (`color: #444`) when inactive and brightens (`color: #d4d4d4`) when active; a small priority number (blush `#e8c4b8`) appears next to the arrow when two or more columns are sorted. Custom ordering: RSVP sorts as attending(0) > pending(1) > declined(2); meal sorts as beef(0) > fish(1) > none(2); date sorts by `dateRaw` (raw ISO string stored on `AdminRow` alongside the formatted `dateSubmitted` display string).
- Export button downloads `EleazMeadRSVP_<datetime>.xlsx` via SheetJS (`xlsx` package).
